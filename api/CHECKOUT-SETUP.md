# Japansterdam checkout setup

The Mollie integration is deployed **disabled**. Public checkout keeps the existing email request until live setup is complete. No bank account, provider subscription or payment method is opened/activated by this code.

1. Register and verify the merchant business and payout account in Mollie. Activate the intended payment methods there.
2. Open the existing **japansterdam-api** Worker in Cloudflare (the shop account, not the separate radar Worker). In Settings → Variables and Secrets, add an encrypted `MOLLIE_API_KEY` with a `test_…` key. Do not put it in Git, chat, Pages content or browser storage.
3. In Japansterdam admin → **Checkout settings**, enter the registered company details and a shipping rate (in euros) per supported two-letter country code. Review delivery, terms, complaints/conformity, returns, return address, privacy and tax wording. VAT/margin/KOR treatment must match the actual business; this checkout does not invent a VAT percentage or generate tax invoices.
4. Save with checkout disabled, mode test. Use **Open private Mollie test payment**. Test success, failure and abandonment; inspect Orders. Test orders never reserve/sell real stock and never email customers. This requires a matching test key. Local automated tests additionally cover actual live-mode reservation transactions using mocked provider calls.
5. Set up a transactional email provider account at Resend and verify the sending domain/DNS. Add encrypted `RESEND_API_KEY` and `ORDER_EMAIL_FROM` (e.g. `Japansterdam <orders@your-verified-domain>`). The owner receipt goes to the contact/notification email saved in Checkout settings. Verify delivery in your own test inbox/provider dashboard before activation.
6. Replace `MOLLIE_API_KEY` with the approved `live_…` key. Change the saved mode to live, review all settings, then explicitly enable live checkout. This toggle is rejected when setup is incomplete. Old test orders cannot be resynced with a live-only key; they remain clearly marked test history.
7. Place a small real test order yourself and verify provider payment, stock, order email, owner email and order overview; refund it in Mollie. Account activation, money movement and refunds are performed by the owner.

## Order processing

Prices and availability come from D1, never from posted browser totals. A single database transaction reserves the complete basket, or nothing. Database triggers prevent concurrent price/stock edits to pending reservations. Payment creation uses one stored body/idempotency key per order; ambiguous provider errors keep stock reserved. Only server-fetched, matching EUR amount/order/mode/ID may mark an order paid. Test mode cannot sell stock. Duplicate callbacks cannot send duplicate receipts. Do not manually release an uncertain payment reservation: first reconcile in Mollie. Unresolved creation older than 50 minutes needs a manual provider check because Mollie idempotency caches have a finite life.

The Worker reconciles pending payments every five minutes. It releases inventory only after a provider-confirmed terminal failure/cancellation/expiry. Confirmations use a durable outbox and stable Resend idempotency keys; bounded retries stop for manual review after 23 hours/5 tries. Refunded or charged-back pieces are **not** automatically relisted. Order data and access tokens are private. The order return URL contains no personal data or access token; the browser retains a random session-only capability.

Orders → Check payment / confirmations refreshes paid refunds and chargebacks and retries pending receipts. Refunds are performed in Mollie, not by the checkout. Fulfillment/tracking is separate from payment. Keep Grailed inventory in sync manually; no automatic Grailed write integration is implied.

The withdrawal form records timestamped requests and queues customer/owner acknowledgements, without automatically accepting a refund or restocking. Full and partial withdrawal text is retained. Wrong/nonmatching order/email combinations return the same generic response. Customer emails include the purchase-time policy snapshot so information remains retainable. Review business/legal texts and data retention with appropriate advisers. A retention/deletion policy for real customer data must be configured operationally; this implementation never automatically deletes statutory records.
